# 官方数据选择与能验证的研究问题

核查日期：2026-10-14。这里的“官方”指数据创建者、论文作者、作者指定的数据存档；本轮没有采用第三方竞赛整理版。

本轮优先接入 **Coat Shopping**，因为它小、有自选评分与随机评分两种观测方式，可以先查清“训练记录偏向哪些商品，改法是否牺牲推荐质量”。随后用 **KuaiRand-Pure** 扩大验证范围，更贴近真实推荐平台的曝光选择。Yahoo R3 保留为扩展数据；当前没有核实可用的官方直接下载，不用来阻挡代码验证。

## 三份数据的取舍

| 数据 | 本轮核实的内容 | 适用问题 | 不能据此声称的结论 |
|---|---|---|---|
| Coat Shopping | 290 名用户、300 件商品；6,960 条自选评分、4,640 条随机商品评分；1–5 星 | 自选样本偏差；商品属性与被选择程度的关系；重加权等改法对随机观测评分的影响 | 完整偏好真值、线上曝光效果、序列反馈或持续自主改进已经成立 |
| KuaiRand-Pure | 27,285 名用户、7,583 个随机候选视频；普通推荐与随机插入两类日志 | 曝光选择、受欢迎程度与推荐质量的联系；多种反馈目标之间的取舍 | 用户对所有视频的偏好都已知；一次离线评分等于新策略线上收益 |
| Yahoo R3 | 原论文确认歌曲的自选评分与随机歌曲评分 | 自选评分偏差、评级预测与去偏方法的外部验证 | 本轮已取得数据或已获现行使用授权 |

Coat 和 Yahoo 的随机观测设计来自 [Schnabel 等的原论文 §6.5](https://proceedings.mlr.press/v48/schnabel16.pdf)。KuaiRand 的数据版本与规模来自 [作者项目页](https://github.com/chongminggao/KuaiRand)。

## Coat：本轮实际核验与使用边界

作者的 [Cornell 发布页](https://www.cs.cornell.edu/~schnabts/mnar/) 提供 [coat.zip](https://www.cs.cornell.edu/~schnabts/mnar/coat.zip)，不需要账号。本轮对官方 ZIP 完成内存下载、文件列表和评分计数检查：

- ZIP：537,499 字节，约 525 KiB。
- SHA-256：`6073d0b515ed1f6e830e4fead66dc76ad7991a7553eaa58e228b234a9d19daed`。
- `train.ascii`、`test.ascii`：都是 290 × 300 的矩阵，非零值分别为 6,960 和 4,640 个；**0 表示未观测，不能当作“不喜欢”**。
- `propensities.ascii`：作者估计的观测概率。README 写明它来自数据拟合，不能当作系统已知的真实概率。
- `user_item_features/`：用户 14 列、商品 33 列的属性编码，并提供列名映射。商品的 `onfrontpage` 表示是否放在首页，不能把它解释成实际曝光次数。

当前 `load_coat()` 已接通真实文件。它从随机评分中排除了 366 个也出现在训练中的用户—商品组合，避免用训练见过的组合充当新验证；默认种子 `20261014` 下，剩余 4,274 条随机评分分成开发 2,065 条、测试 2,209 条，290 名用户在两侧都有观测。划分在每位用户内部独立打乱，因此每人的奇数个余项留给测试，整体数量不完全相等。这不是时间外推，也不是新用户验证。

发布页将数据和代码指定为 [CC BY-NC 4.0](https://creativecommons.org/licenses/by-nc/4.0/)：研究交付应保留作者、来源与许可说明，修改时标明修改。

原实验让用户在商店界面寻找想买的衣服，之后对 24 件自己探索过的衣服和 16 件随机衣服评分。用户属性包括性别、年龄段、地区、时尚兴趣；商品属性包括目标性别、衣服类型、颜色、首页展示。数据没有连续曝光记录，也没有语义丰富的商品描述，所以它适合检查去偏研究闭环，不能直接替代 AgentCF 的全部训练情境。[原论文 §6.5](https://proceedings.mlr.press/v48/schnabel16.pdf)

### 建议如何接入系统

1. **训练只读自选评分。** 随机评分先分成研究开发用部分和封存测试部分；训练程序不能把它们写进用户记忆。
2. **先比较观测方式。** 查看哪些商品或属性在自选记录中过多出现，提出至少两种解释，例如偏好差异与界面展示差异；数据差异本身不能判定哪个解释正确。
3. **让改法接受质量检验。** 可以比较普通训练、观测概率重加权、受欢迎度调整。若把热门商品压低，热门占比自然可能下降，所以还必须看随机观测上的质量变化。
4. **开发阶段选方案，测试阶段只验一次。** 固定方法、参数和评价方式后，再读封存测试评分；不能看到测试结果后继续用同一批评分挑方案。
5. **把失败写回研究日志。** 例如“偏差指标下降但质量损失过大”，下一轮应尝试更温和的权重或重新检查解释；不能把失败改写成成功。

随机评分只揭示一小部分用户—商品组合。若只在这部分已评分候选里计算 NDCG，必须命名为“随机观测候选内排序”，不能写成“全目录推荐效果”。未评分项继续保持未知。原论文使用的观测概率重加权也依赖估计是否可信；可同时报告不用权重的随机观测评价，避免只靠一个估计器解释结果。[方法原文](https://proceedings.mlr.press/v48/schnabel16.html)

## KuaiRand：下一阶段的真实曝光验证

作者提供的 [Zenodo 数据记录](https://zenodo.org/records/10439422) 可以公开访问。数据大小与许可先通过 HTTPS 记录 API 核实，并保留证书验证；元数据核查不等同于完整文件下载和校验，实际取得情况以本地 `source.json` 与运行报告为准。

| [KuaiRand-1K.tar.gz](https://zenodo.org/records/10439422/files/KuaiRand-1K.tar.gz) | 1,135,436,720（约 1.06 GiB） | 约 4.3 GB |

Zenodo 记录中的数据许可为 **CC BY 4.0**；作者 GitHub 项目的仓库许可为 **CC BY-SA 4.0**。这是两个发布对象，应分别保留来源，不要互相覆盖。体积和许可可通过 [官方记录 API](https://zenodo.org/api/records/10439422) 复查。

Pure 保留候选池中的普通推荐和随机日志，共有 1,436,609 条普通推荐交互及 1,186,059 条随机交互。它适合先做小规模去偏验证，但普通推荐序列被筛过，不宜声称完整还原长期反馈。作者也把完整序列研究指向 1K / 27K 版本。[作者版本说明](https://github.com/chongminggao/KuaiRand#three-versions-and-suggestions)

日志有点击、喜欢、播放时长等反馈；特别要注意 `is_click` 的含义会随页面改变，单列页面中它表示有效播放，而不是手指点击。开始实验时应固定一种反馈和一种场景，按时间划分开发与测试。不能把没有曝光的视频补成负反馈，也不能把随机插入记录扩展成完整效用矩阵。[官方字段说明](https://github.com/chongminggao/KuaiRand#data-descriptions)

当前 `load_kuairand()` 的预定规则是：只从 4 月 8–21 日普通推荐日志选用户，按种子哈希确定 200 人，每人保留最近 200 条训练事件；随机曝光中 4 月 22–30 日用于开发，5 月 1–8 日用于测试。用户选择不依赖未来有没有正反馈。它保留真实的零反馈，每个分区的重复组合只取时间最早的一条，并去掉训练已见组合及开发、测试之间的重复组合。热门程度也只由保留的训练事件计算，不借用整月统计。Pure 的页面含义混合仍须在报告说明；后续可预先选定页面再验证，不能看到哪种页面效果好才事后筛选。

本轮已按该规则读取完整官方文件：扫描 1,141,112 条训练期日志和 1,186,059 条随机日志，从 26,210 个训练期用户中选出 200 人。实际保留训练 8,334 条、开发 2,459 条、测试 5,511 条；训练历史上限移除 37 条，随机记录中的训练已见组合移除 3 条。开发与测试分别支持 171 / 198 名用户，其中有正反馈的用户为 101 / 146 名。没有观测或没有正反馈的用户数量也须报告，不能偷偷删除后声称覆盖所有用户。零反馈分别为训练 4,138 条、开发 1,936 条、测试 4,527 条，均真实保留。

## Yahoo R3：保留，暂不作为本轮必要条件

[原论文 §6.5](https://proceedings.mlr.press/v48/schnabel16.pdf) 说明它包含超过 30 万条自选歌曲评分，以及部分用户对随机歌曲的评分。本轮访问 [Yahoo Webscope 官方目录](https://webscope.sandbox.yahoo.com/catalog.php?datatype=r) 未取得可用页面，未获得现行直接下载地址和文件大小。

Yahoo 官方存储域名中的 [历史研究说明](https://yahoo-webscope-publications.s3.amazonaws.com/Rating_music.pdf) 记录了签署 Data Sharing Agreement、学术研究用途及禁止再发布的限制。这只能证明历史条款，不能替代当前许可确认。因此本轮不下载第三方副本，也不把它装进代码包。

## 对“大目标 RSI”怎样计证据

本项目把 RSI 理解为系统根据研究结果，持续改进自己的研究与推荐方法。数据接入之后，应分别回答三件事：

- **流程可运行吗？** 真实数据能读入，研究计划能执行，独立评分和日志能完成。
- **某个改法有用吗？** 在预先定义的偏差指标上改善，同时满足质量限制，并在封存数据上仍可观察。
- **迭代本身有用吗？** 多轮反馈后，系统更会提出解释、选择实验、避开已失败方向；需要与固定策略、无历史反馈或同预算搜索比较。

前一项通过不能替后一项通过。单次去偏有效也不能自动证明 RSI。真实数据的价值，是让系统学会承认未知、区分解释、利用失败结果，而不是把模拟环境里的“已知偏好”换一个名字继续使用。
