# 把推荐系统研究员应用到真实数据

本轮要回答的是：系统能否在真实推荐数据上发现热门倾斜，提出有明确预期的改法，读取实际结果后修订下一轮实验，并把研究方法的修改带到另一份数据上检验。

程序执行完成、推荐器改善、研究策略改善是三件分别判断的事。本文说明实验设计和运行方法；实际完成情况、请求数、失败记录和效果，以运行目录中的报告及 JSON 记录为准。

## 1. 为什么先用这两份数据

| 数据 | 官方来源 | 本轮用途 | 为什么适合 |
|---|---|---|---|
| Coat Shopping | [作者数据页](https://www.cs.cornell.edu/~schnabts/mnar/) | 首轮开发与冻结候选验证 | 同一批用户同时有自行挑选物品的评分和随机物品评分，可以把带选择性的历史与随机观察面板分开 |
| KuaiRand-Pure | [项目官网](https://kuairand.com/) | 研究策略迁移对照 | 来自真实短视频平台，有普通曝光日志和随机曝光日志，可以检验从购物数据学到的研究安排是否还有帮助 |

Coat 较小，适合先跑通并看懂每一轮。KuaiRand-Pure 用按训练用户 ID 选定的小规模用户组，训练历史长度有明确上限，先验证可行性，不要求服务器或 GPU。完整来源、许可和数据限制见[官方数据选择](官方数据选择.md)及下载目录的 `source.json`。下载器记录原始包的校验值，用来核对本次实际用了什么文件。

这里的“随机”指数据作者随机安排的物品或曝光，不代表每个用户对整个目录的喜好已被完整观察。我们只评价这些真正观察过的候选物品。

## 2. 数据怎样进入系统

系统统一使用三列：`user` 是匿名用户编号，`item` 是匿名物品编号，`rating` 是已观察反馈。推荐器只接收训练反馈；排名时只接收用户和候选物品编号。开发、验证标签交给独立评分程序。

**两份数据的 0 含义不同，不能混用：**

- Coat 矩阵中的 `0` 表示没有评分。读取器把它剔除，不能说用户不喜欢。
- KuaiRand 的 `is_click=0` 是一次已经发生的曝光反馈，读取器保留它。它计入训练曝光次数，但不进入正反馈共现；其具体点击、有效播放含义还受界面形式影响。

Coat 的训练集保留非零自行选择评分。随机评分中已经出现在训练里的用户物品对先剔除，再按固定种子逐用户分成开发、验证两部分。它验证已知用户的新物品对，不是时间外推或新用户测试。

KuaiRand-Pure 按时间区分：4 月 8—21 日普通曝光训练，4 月 22—30 日随机曝光开发，5 月 1—8 日随机曝光验证。用户只根据训练期 ID 选择，不按未来是否点击筛选。每个用户最多保留 200 条最近训练事件；剔除训练期已见对和开发、验证之间重复的用户物品对。同一分区重复曝光保留最早事件，避免挑最好看的标签。所有筛除数量都写入数据统计。

两个数据集都重新训练自己的推荐器。迁移的是研究策略，不是把 Coat 的物品模型直接套到短视频上。

## 3. 研究对象与改法

这轮加入第二个研究对象 **ItemCF**，即“根据用户共同喜欢过的物品，寻找相近物品”。它是一个普通 CPU 推荐器，便于用真实反馈快速检查工作流。AgentCF 的推荐与记忆研究路径继续保留，本轮没有把 ItemCF 结果说成 AgentCF 数值复现。

ItemCF 用训练正反馈计算物品相似度，每个物品保留 40 个相近物品。Coat 评分至少 4 分算正反馈，KuaiRand 使用 `is_click=1`。训练中没有形成个性化相似分数时，回退到物品训练均分；没有物品均分时用全训练均分。全部训练为空时按稳定物品编号排序。

热门程度只用训练中已观察反馈的条数，目录中观察次数最多的前 20% 作为热门组。Coat 的一条记录是一次评分，计数表示“被评分频次”，不能当成真实曝光次数；KuaiRand 的一条记录来自曝光日志，计数则是本轮保留历史里的曝光频次。两者都是带原平台选择影响的历史代理，不是真实喜好。输出改法有三个：

| 动作 | 实际改变 | 想验证的问题 |
|---|---|---|
| `retain` | 保留原版排序 | 当前是否缺少足够证据支持修改 |
| `popularity_penalty` | 在原推荐分数中扣除一定强度的热门惩罚 | 额外热门倾斜是否能通过轻量重排减少 |
| `user_calibrated` | 对历史正反馈更偏热门的用户减轻惩罚 | 一刀切惩罚是否伤害了部分用户，按用户历史调整是否更合适 |

原分数和热门惩罚都按固定训练目录缩放。换一个开发或验证候选面板不会改变同两件物品的相对次序。`strength` 是惩罚强度，越大越压低热门物品；研究员只能从当前允许的强度列表中选择。

用户历史本身可能受原平台曝光影响，所以“用户训练期更偏热门”只是一个可用历史线索，不能当成用户真正偏好的答案。

## 4. 一次自主研究怎样运行

每轮由真实语言模型提出实验，普通程序负责执行和评分。模型不会给自己评分。

1. **看证据。** 读取原版开发指标、各类受损或受益用户案例、数据的适用范围。不能读取验证评分。
2. **提出可失败的解释。** 写出主要解释、竞争解释、预期变化，以及什么结果会推翻这次判断。当前是小范围的干预比较；一次惩罚实验仍可能同时符合多种解释，不能自动判定原因。
3. **选择一个动作。** 输出具体 `operator` 和 `strength`，并说明为什么这次行动有助于区分解释。
4. **执行和评分。** CPU 推荐器产生完整候选排列，独立程序计算质量、热门倾斜和长尾表现。
5. **读结果再安排。** 模型看到实际变化、质量代价和失败案例，修订判断并提出下一轮方向。完整历史臂会把这些信息带到下一轮，同时把前轮提出的下一动作放进 `next_action`。新计划可以采纳，也可以说明理由后改动；`plan_handoff` 保存建议、实际动作及是否一致，便于检查反馈有没有真正影响安排。

“自主”在本轮指模型根据证据安排预先实现的改法，执行过程无需人为逐轮挑参数。当前还不是开放式编写任意推荐算法。每个候选的具体改动、模型解释和外部结果分别保存，便于检查模型是否真的因反证而改计划。

## 5. 怎样设置对照，怎样冻结验证

### Coat：同数据、三种研究安排

| 组别 | 候选数 | 真实模型请求 | 用途 |
|---|---:|---:|---|
| 带研究历史 | 3 轮 | 每轮计划与总结各一次，共 6 次理想请求 | 看前轮证据能否帮助后轮实验 |
| 无研究历史 | 3 轮 | 同样共 6 次理想请求 | 每轮看不到前轮结果，检查历史反馈的作用 |
| 固定策略 | 3 个 | 0 次 | 固定热门惩罚强度 `.05`、`.1`、`.2`，检验简单现成方法已有多强 |

无历史臂的每轮仍执行候选并总结，但结果不带到下一轮。这个对照去除的是跨轮研究记忆，不是删掉当前数据证据。

程序还会识别重复改法：在相同数据、推荐器和参数下重复提案，直接复用同一份 CPU 排名与评分。提案仍占当前臂的一轮，计划和总结仍各调用一次模型；复用不算独立重复验证。因此需要同时看“候选提案数”“实际不同改法数”和“模型请求数”，不能把反复提同一改法算成多份独立证据。

固定策略与模型臂只匹配候选次数。CPU 执行时间与语言模型的调用成本不同，不能声称三组的总计算成本完全相同；报告会分别列出候选执行与模型请求。

各组根据开发结果选定唯一候选，保存具体改法，再对验证面板评分。验证期间不让模型重选强度。若开发没有合格候选，明确保留原版；不靠反复查看验证结果来挑方案。

### 从 Coat 更新研究策略，再到 KuaiRand 对照

Coat 结果交给模型后，额外一次请求输出 `strategy_revision`。研究策略的版本变化必须具有实际用途：

- `strength_grid`：下一份数据允许探索哪些惩罚强度，程序用它约束候选选择。
- `evidence_focus`：下一份数据优先呈现哪类诊断证据，程序用它调整研究员收到的证据视图。
- `preferred_operator`：交给下一任务研究员的优先行动提示。它影响提案输入，但不是强制执行命令；实际采取什么改法仍要看每轮计划。不要把“写了一个偏好”当成已经改变了推荐器。

随后在同一 KuaiRand 用户组上分别运行原策略 v1 和修订策略 v2，各 2 轮、各 4 次理想模型请求。推荐器、数据划分、模型设置、每臂候选数相同；两臂也读取相同的 Coat 源任务经验，避免只有 v2 知道前一任务发生过什么。两臂都按开发选择、冻结后验证，再比较结果。

这样能够检查“改了研究安排以后，在另一任务上是否更有帮助”。单纯改候选强度属于推荐器优化；只有模型产生的策略修改被实际执行、并有原策略对照，才开始接近研究系统自身改进的证据。

Coat 的留出反馈用于这次策略修订以后，就成为研究系统的训练经验；它仍是该次推荐候选的留出评价，却不是整个元研究过程最终未见的数据。KuaiRand 的最后一段随机反馈在 v1/v2 选定候选前不可查看。若看完它再改研究策略，后续需要另留新任务或新时间段评价，不应继续把这一段称为最终封存数据。

### 调用安排

理想请求数为：Coat 两臂 12 次，策略修订 1 次，KuaiRand 两臂 8 次，共 **21 次**。总上限 **30 次**，包括格式错误等重试。实际次数以调用记录为准；若接口不可用或预算耗尽，保留已经完成的记录，不把未完成部分算作成功。

## 6. 怎样读结果

主质量指标是观察面板上的 NDCG：真正评分或反馈更好的候选排得越靠前，分数越高。它衡量这些观察候选的排序质量，**不是整个物品目录的真实偏好质量**。

主偏差代理是“面板额外热门曝光”：推荐排序对热门物品的加权曝光，超过按该面板真实观察反馈排序时应有的热门曝光多少。理想排序中同分物品的热门份额取平均，避免随意按物品编号打破同分就产生假偏差。额外倾斜之外还报告有符号差异，便于发现过度压低热门物品。

同时报告热门曝光份额、长尾相关物品召回、逐用户变化和实际支持人数。没有可评价正收益或没有长尾正例的用户单独计数，不悄悄丢弃。

候选先按两个独立点门槛判断：

- 质量至少保留原版的 **99%**。
- 面板额外热门曝光降到原版的 **90% 以下**；原版几乎没有该偏差时不作可靠相对去偏判断。

“点门槛通过”只表示这一份数据的均值满足约定。用户配对重抽样区间会另外报告：反复抽取用户，查看平均差异大概有多不稳定。区间不因点门槛通过就自动通过，也没有消除开发过程中试多个候选带来的选择影响。

除了各臂相对原推荐器的变化，`campaign.json` 还保存两种直接比较：`direct_controls` 比较带历史研究员与无历史研究员、固定规则的冻结结果；`strategy_transfer_comparison` 比较 KuaiRand 上 v2 与 v1 的冻结结果。这些比较使用同一批用户、标签和面板，输出质量差异、偏差差异和配对区间。它们是一次探索性对照，不能当成重复多个任务后已经建立的稳定 RSI 结论。

随机观察面板改善可以支持小规模可行性，但不能直接证明平台线上收益、长期反馈变化或所有类别的 bias 都被解决。当前专门研究热门倾斜，不能把结果扩写为全面去偏。

## 7. 实际使用命令

在项目根目录运行：

```powershell
python -m pip install -r requirements.txt
python -m rsi_researcher fetch-data --dataset coat --output data/external/coat
python -m rsi_researcher fetch-data --dataset kuairand-pure --output data/external/kuairand-pure
```

下载命令访问官方来源；推荐器执行和评分在本机 CPU 完成。研究计划与总结通过模型 API 生成，需要用户环境中的 `DEEPSEEK_API_KEY`。密钥不写入配置文件或实验包。若已经配置 Windows 用户环境变量，但当前终端尚未读取它，可只把它加载到当前进程：

```powershell
$env:DEEPSEEK_API_KEY = [Environment]::GetEnvironmentVariable("DEEPSEEK_API_KEY", "User")
python -m rsi_researcher study --config configs/official_study.json --output runs/official-study-20261014
```

同一输出目录保留一次研究的完整记录。再次运行请使用新的目录名，避免把两次运行混成一次。

主要记录位置如下；模型写出的解释和程序算出的结果分开保存：

```text
运行目录/
├── campaign.json                     全批状态、数据来源、对照差异和请求数
├── report.md                         便于阅读的批次报告
├── with_history/                     Coat 带历史研究
│   ├── baseline.json                 原版开发评分和评价规则
│   ├── trials/0001/
│   │   ├── observed_plan_input.json  研究员实际读到的证据和下一动作
│   │   ├── observed_plan.json        模型提出的假设和具体改法
│   │   ├── candidate.json            程序计算的逐用户评分
│   │   ├── observed_learn.json       模型读结果后的判断与下一行动
│   │   └── archive.json              提案、指标、复用标志和行动衔接
│   ├── frozen_candidate.json         读最终反馈前冻结的唯一改法
│   ├── validation.json               最终面板上的结果摘要
│   └── validation_scores.json        用于直接配对比较的完整程序评分
├── without_history/                  Coat 无历史研究
├── fixed_control/                    Coat 固定三个强度对照
├── strategy_revision/                根据源任务结果生成的策略 v2
├── transfer_v1/                      KuaiRand 原研究策略
└── transfer_v2/                      KuaiRand 修订研究策略
```

文件存在不代表整批已经成功：先看 `campaign.json` 的状态，再看每臂 `archive.json` 和 `validation.json`。若某臂中断，已经执行的排名与指标仍然有价值，但尚未完成的总结或验证不能补写成完成。

## 8. 代码从哪里读

| 文件 | 做什么 | 为什么拆开 |
|---|---|---|
| `rsi_researcher/datasets/coat.py` | 读取 Coat、剔除缺失值与训练重叠、固定随机划分 | 不让推荐器自己决定哪些标签算观测 |
| `rsi_researcher/datasets/kuairand.py` | 选训练用户、按时间划分随机曝光、保留已曝光未点击 | 把时间、重复曝光和缺失语义写清楚 |
| `rsi_researcher/recommenders/itemcf.py` | 训练 ItemCF、执行候选改法、只读取候选 ID 排名 | 排序程序接触不到留出标签 |
| `rsi_researcher/evaluation/observed.py` | 独立面板评分、逐用户差异与区间 | 模型解释与效果判断分开 |
| `rsi_researcher/research/benchmark.py` | 安排研究臂、传递证据、冻结候选、实际应用策略修订 | 把研究流程与某个具体推荐器的分数计算分开 |
| `configs/official_study.json` | 固定轮数、预算、数据路径和允许强度 | 研究开始前可以看清本次打算怎样比较 |

本轮首先核验真实数据、真实模型、执行程序和外部反馈之间是否形成可审阅的闭环。推荐器指标改善和研究策略改善分别报告；小样本跨数据对照属于 RSI 的探索证据，不能仅凭流程走完就说已经证明 RSI。

Coat 说明轻量改法在这份留出数据上可以兼顾质量与该偏差代理，但带历史研究员没有超过固定规则。KuaiRand 两种策略都未满足质量约束。v2 比 v1 保留更多质量，同时剩余额外热门倾斜也更多，是取舍变化，不是全面胜出。这批数据不支持“自主迭代已经实现稳定 RSI”的结论。

### 科研解释错误不能靠执行成功掩盖

审核原始模型文本发现了跨任务误读：Coat 用户 `216`、`0` 的受损案例被带进 KuaiRand 的研究上下文，模型把它们当成当前要修复的用户，并在部分预测中继续采用 Coat 的基线质量 `0.6923`；KuaiRand 当时的开发基线实际约为 `0.4503`。不同数据里的匿名编号不能配对。同样出现约 `-0.63` 的质量差异，也不能据此断言损失“转移”到另一批用户或跨任务“逐位不变”。

另有一轮模型谈论要检验内容或共现的新方案，但实际动作是 `retain`。程序只执行了保留原版，因而新方案根本没有接受实验。模型还把少数已测改法的不确定结果扩写成“该面板不存在可用去偏机制”；这种结论超出了有限的候选范围。质量差异区间跨过 0 表示方向仍不确定，不能证明没有可用方法，也不能证明“质量损失不超过预先允许范围”已经成立。

这些问题发生在研究上下文和解释层。程序独立产生的排名、评分及留出门槛仍按实际数据执行；检查没有发现把最终评分标签输入推荐器或用于挑选该次候选。应保留数值记录，降低对模型解释和策略迁移结论的信任，不能把错误叙事包装成机制证据。

### 根据实际失败修改，再做接入检查

修正方向是：跨任务只迁移前任务的政策、策略和汇总对照，不搬运用户案例或完整解释文本；当前用户案例标明所属数据和任务；阈值与受损案例必须来自当前任务；每轮只解释实际执行的改法。这样把“过去学到的一条研究经验”与“当前观察到的证据”分开。

在原总请求上限内已完成补充检查。第一次新增 4 次请求，因为总结连续选择网格外强度而失败；修正总结输入与重试反馈后，第二次新增 4 次请求，两臂流程完成，均因质量损失过大保留原版。加上主批 22 次，总共正好 30 次请求。两次检查使用同一新用户组，但与主批的用户组和轮数不同，不能把批次指标差异归因于上下文修复。

完成后的文字审核仍发现模型把原版零差异误读成上一轮无改动实验、混淆质量可评价与零理想增益用户。当前源码删除首次证据里的零变化量，只给出原版表现，并增加人数定义；最后这项修改只完成本地测试，尚未用真实模型再次检查。因此流程已验证可执行，科研解释仍须逐条对照实际证据。
