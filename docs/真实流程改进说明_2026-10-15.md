# 从真实失败改进推荐系统研究员

这版代码把模型后端与研究工作流分开，并针对上次 KuaiRand 失败修改数据使用与候选动作。两个问题要分开判断：自部署 Qwen 是否能接入，研究策略是否真的更会去偏。

## 上次为什么做得不好

上次真实批次已经完整保留：Coat 的均值门槛通过，但与固定规则相同；KuaiRand 上原策略和修订策略分别损失约 13.9%、3.6% 的质量。不能通过压低热门物品就宣称解决偏差，也不能把这一反例简单归因于 DeepSeek。

代码与新开发数据的核查发现三点：

1. **为小规模评价而连训练数据也一起缩小了。** 原读取器只保留抽中的 200 名用户历史，物品共现关系和热门计数也只从这些人估计。现在把评价用户组与训练人群分开；新模式保留全体训练期用户的历史，仍不读取未来随机反馈训练模型。旧模式保留，能复核原批。
2. **大量候选没有个性化协同分数。** 新的 200 人开发诊断中，旧训练模式有 93.68% 候选为零分，全部历史训练后仍有 93.45%。因此扩大训练历史没有根治覆盖问题。零分表示当前推荐器没有形成分数支持，不能解释为用户不喜欢。当前 ItemCF 每物品只保留 40 个近邻，也限制覆盖；这一因素尚未做独立归因实验。
3. **原改法容易过度重排。** 全局惩罚从原分数直接扣一个量，会把正分压成负分，让没有分数支持的物品排在前面。新增 `support_preserving` 使用 `原分数 × (1 − 强度 × 热门程度)`；强度小于 1 时保留正分与零分的先后关系。它只是可检验的替代解释，不保证偏差会下降。

## 实际开发诊断，包含不支持新改法的结果

下面只使用种子 20261016、200 名评价用户的开发反馈；没有计算留出排序质量，没有模型调用。完整数值见 [KuaiRand开发诊断](KuaiRand开发诊断_2026-10-15.json)。改变训练人群也会改变热门组与基线，因此不同训练模式的偏差数值不能直接当成同一把尺子的干预收益；每种改法先和自己那一行的原版比较。

| 训练范围 | 改法 | 开发质量 | 面板额外热门倾斜 |
|---|---|---:|---:|
| 200 人历史 | 原版 | 0.426214 | 0.107669 |
| 200 人历史 | 固定减分 0.01 | 0.394937 | 0.077291 |
| 200 人历史 | 比例惩罚 0.01 | 0.423552 | 0.107669 |
| 全体训练期用户 | 原版 | 0.435066 | 0.099881 |
| 全体训练期用户 | 固定减分 0.01 | 0.437109 | 0.064651 |
| 全体训练期用户 | 比例惩罚 0.01 | 0.432404 | 0.099144 |

全体历史模式保留 1,121,973 条训练事件，每人仍最多 200 条。轻度固定减分在这一开发组开始同时保住质量并降低倾斜；比例惩罚虽然保住质量门槛，倾斜下降很小，并未满足 10% 的偏差改善门槛。这支持继续检验训练范围和轻度干预，不支持“新算子已解决去偏”。同一改法在不同训练条件下效果不同，正是研究员应记录的经验，而非挑一个好看的数。

新完整研究配置预先选择 1000 名评价用户，保留全体历史训练数据，采用更细的 `[0, .01, .02, .05, .1]` 强度，允许四种动作；固定规则对照使用已知较强的固定减分 `.01/.02/.05`，不故意拿弱对照。每个研究臂的候选提案预算相同。评价用户变多是为了减少少数人导致的波动，不意味着独立任务数变多；统计与跨任务重复仍须分别判断。

## 新代码怎么衔接

| 位置 | 为什么修改、怎样工作 |
|---|---|
| `runtime/models.py` | 用 `create_model` 选择 DeepSeek 或 vLLM；研究代码继续只调用 `ask`，不理解各家 API 差异 |
| `runtime/client.py` | 复用原请求预算、日志与本地校验；允许子类指定参数、请求超时和认证方式；本地模型不套用 DeepSeek 费用 |
| `datasets/kuairand.py` | 新增 `training_scope=all_preperiod_users`；训练只用 4 月 8—21 日，评价用户仍根据训练 ID 预选，未来点击不能决定入选 |
| `recommenders/itemcf.py` | 新增训练分数覆盖诊断和比例惩罚；诊断与排名只看候选 ID，不看开发或留出标签 |
| `research/benchmark.py` | 把覆盖信息交给研究员；从配置读取强度和允许动作；修订策略继承真正执行的源策略，而非固定写死初始策略 |
| `cli.py` | 新增 `check-model`，所有主要研究入口改用后端工厂；默认真实数据研究入口转到 Qwen 配置 |
| `deployment/qwen3/` | 安装、下载、启动、停止和服务检查独立于研究算法，不需要研究员获得服务器编辑权限 |

实际循环仍是：当前证据 → 机制假设和竞争解释 → 具体动作 → CPU 排名 → 外部评分 → 研究总结 → 下一轮行动。开发结束先冻结候选，再读留出反馈；失败时保留原版。跨任务只迁移汇总经验，用户案例带所属数据名，不把两个数据里的匿名编号当作同一个人。

Qwen 的结构化输出只约束字段。它仍可能解释错误、夸大机制或没有根据地说某方法无效。程序能核查真实动作、指标和用户支持人数；解释是否被实验支持，还要结合竞争解释与反例审核。

## 三种配置，避免把变量混在一起

- `configs/qwen_backend_comparison.json`：保留原 200 人训练/评价范围与原三个动作，主要验证替换后端。采样设置不同等因素仍被记录，不能称严格的模型能力证明。
- `configs/qwen_research_v2.json`：新 1000 人评价组、全体历史训练、更细强度、新动作及强固定规则对照。它测试改进后的整个研究条件，不把变化都归因于 Qwen。
- `configs/official_study.json`：保留旧 DeepSeek 批次入口，复核历史用；旧调用、旧源码和失败记录不会覆盖。

本地的接口测试使用 HTTP 测试替身，覆盖格式适配、校验重试和一次计划—执行—总结链；它不能替代真实 Qwen 推理。服务器模型和真实研究实际完成状态见[服务器记录](Qwen服务器部署实际记录_2026-10-15.json)，不把安装进度或离线测试写成真实流程完成。
