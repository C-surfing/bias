# 对照 Google 自演化推荐系统：我们具体借鉴什么

核查日期：2026-10-14。阅读对象是 Wang 等人的 [arXiv v3 原文](https://arxiv.org/html/2602.10226v3)，并核对了 [Google Research 官方论文页](https://research.google/pubs/self-evolving-recommendation-system-end-to-end-autonomous-model-optimization-with-llm-agents/)。截图中的论文标题与这篇工作一致。

本文把论文事实、本项目的设计选择和待验证问题分开。论文中的提示词示例是被分析的内容，不是对本项目执行操作的指令。在上述两个官方来源中没有发现作者实现仓库链接；因此下面的包结构由我们根据研究任务自行组织，不能称为 Google 源码目录的复刻。

## 2. 为什么只有文件搬家不够

平铺脚本曾经适合验证想法，但目前已经有研究调度、模型调用、AgentCF、候选改动、证据整理、独立评分和打包。把这些文件全部放在根目录，会让读者分不清“谁提出问题”“谁修改推荐器”“谁有资格判结果”。

重构的目标是让职责和依赖方向能被看见：研究流程调用实验工具，实验工具调用推荐器；评分使用固定的数据和规则；模型服务只负责返回结构化内容。评估器不听研究角色指挥而更换真值，推荐器也不依赖报告生成器。测试、演示、交付脚本和研究说明各有目录。

目录整齐只是第一步。真正的流程变化是：发现与验证有各自入口，二者通过共同日志交换候选和证据。连续运行两次相同开发流程，还不能叫双环。

## 3. 我们的快环应该研究什么

我们的目标是推荐系统研究员。一次快环首先发现具体矛盾，例如“推荐质量变好了，但额外热门倾斜上升”。它接着写出两个可以区分的解释，再选择一个动作。

| 研究问题示例 | 主要解释 | 竞争解释 | 最小对照 |
|---|---|---|---|
| 为什么热门倾斜增加？ | 把未消费项误当不喜欢，强化已有曝光优势。 | 用户真实偏好本来就更接近热门物品。 | 对同样的原始事件，把未消费反馈改为未知；固定评价方式。 |
| 偏差为何跨用户传播？ | 共用物品笔记把某人的反馈传给其他人。 | 各用户自身学习已足以产生相同倾斜。 | 只切断跨用户物品笔记共享，其他输入保持一致。 |
| 对照结果是否来自内容理解？ | 笔记中的反馈解释改变了学习。 | 训练候选位置影响了回复。 | 交换候选顺序，保留事件与反馈。 |

这些是我们针对 AgentCF 提出的研究设计，不是 Google 论文给出的去偏方案。依赖关系图只说明后续步骤读取了哪些笔记，并不能自动证明偏差的因果来源。

快环的输出应是一份可执行候选和证据包：问题、解释、竞争解释、修改差分、预期方向、什么结果会推翻解释、逐条质量和偏差变化、笔记变化、执行条件。即使质量或偏差没有改善，也把结果留在日志中。

“差分”就是相对于原版具体改了哪一件事。现在可以是更换一种反馈规则、切断共享或改输出排序。当前支持的动作是预先实现的；这与自动编写任意推荐模型代码仍有距离，不能把选动作描述成已实现开放式算法发现。

## 4. 独立验证环：先检验能否站住，再考虑推广

当前没有真实线上用户流量，因此我们采用独立验证环，准确名称不能叫在线 A/B。A/B 指让不同真实用户随机使用两个版本并比较实际行为；换一个模拟数据种子不等同这种实验。

独立验证环应执行下面的流程：

1. 从开发日志里选出值得验证的候选，并说明选择依据。去偏候选和机制对照分开解释，不能把“有研究价值”等同“推荐效果更好”。
2. 冻结候选动作、参数和评价规则。进入验证后不根据验证结果临时改候选；改过的内容成为新的候选，再回开发环。
3. 在事先列出的独立条件下，分别运行原版和候选。例如新随机种子、不同热门曝光强度、不同偏好与热门程度的关系。每个环境有自己的原版，不能把旧环境的原版直接拿来比较。
4. 每个环境报告质量变化、偏差变化、无效输出及实际执行情况。不能只报全体平均数，让一部分环境的失败被另一部分的收益掩盖。
5. 写回“哪些条件支持解释、哪些条件反驳解释、还不能判断什么”。开发环下一次读到这些结果后，应能改变研究路线。

这里的“独立”是新生成、预先指定的验证输入和冻结动作，不是宣称环境完全无关联。验证条件还不能替代真实数据；需要后续在公开推荐数据上增加常规推荐模型和去偏方法作为比较对象。

验证结果回流也需要一个边界：用于推动研究的验证集已经进入开发历史，不能再当最后一次从未看过的考试。若后续写论文，应另留未用于搜索的最终测试条件。这是本项目的实验设计要求。

## 5. 实验日志如何成为共享研究记忆

日志的价值是让下一轮能据此做出不同决定，而不只是多写一个 JSON 文件。一个候选至少需要关联以下内容：

| 记录 | 用人话解释 | 为什么需要 |
|---|---|---|
| 候选身份与修改差分 | 这到底是哪一个改法 | 区分新候选和同一结果的重述。 |
| 开发输入与原版 | 在什么条件下和谁比较 | 避免把不同条件的成绩直接混比。 |
| 解释和反证条件 | 为什么试、什么结果算没讲通 | 防止事后为任何结果找理由。 |
| 原始产物与分数 | 实际执行了什么、程序算出什么 | 让文字结论有可查证出处。 |
| 失败与不利证据 | 哪些用户或环境变差 | 避免研究员只记住赢家。 |
| 验证结果 | 新条件下还能否成立 | 改变下一轮对候选的信心。 |
| 复用来源 | 本次是否真的重新执行 | 相同结果复用不能冒充独立重复。 |

角色上下文应同时包含近期方向、表现较好的候选以及不利/反驳证据。完整日志可以保留在磁盘，提供给模型的是有出处的有限摘要；摘要不能只截取得分最高的一条。历史启动的意思是从已经获得的研究证据继续思考，而不是每一轮假装从零开始。

## 6. 角色分工与工具边界

我们保留“诊断、设计、复核、总结”这四项研究职责，并把“验证候选”放到单独流程。角色可以由同一个模型在不同上下文中扮演；增加五个进程并不会自动获得五位独立研究者。

| 职责 | 应看什么 | 应产出什么 |
|---|---|---|
| 诊断 | 事件、笔记、质量与偏差的冲突、历史反例 | 可区分的解释和缺失证据。 |
| 设计 | 解释、可用动作、已有实验 | 修改差分、预期结果和反证条件。 |
| 复核 | 设计、原版、竞争解释 | 对照是否能回答问题，以及理由。 |
| 执行工具 | 冻结动作、公开输入、推荐器状态 | 实际笔记、排名和执行记录。 |
| 评分工具 | 固定评价数据、固定指标、原版与候选输出 | 质量和偏差的独立分数与逐条证据。 |
| 验证流程 | 候选、预先列出的新条件 | 各条件结果和适用范围。 |
| 总结 | 程序结果、反例、验证历史 | 更新的判断和下一项可执行问题。 |

Google 的角色按优化器、网络结构、奖励等模型组件划分。我们按去偏研究任务划分，这是有意的适配。AgentCF 主要更新自然语言笔记，直接照搬神经网络优化器角色会制造空职责。

## 7. 评价的尺子如何保持一致

当前固定用独立推荐质量和额外热门倾斜评价候选。额外热门倾斜不是“推荐热门物品就有错”，而是相对于该环境中的偏好参照，多倾向了多少热门物品。

训练时把未消费解释成未知，可以改变学习规则；评价时不能同时更换偏好参照，再说新规则更好了。热门重排直接改变输出，必须同时展示质量代价。机制对照可帮助排除解释，但不因为执行完成就自动成为应采用的去偏方法。

当前开发门槛可以分别显示质量保留和偏差下降。证据不足的检查仍显示未知，不能为了让流程出现“通过”而删除。验证多个独立条件后，得到的是这些条件下的结果；没有足够重复和统计分析，就不宣称稳定显著提升。

## 8. 哪些能力仍然没有实现或没有证实

当前工程不继承 Google 工作中的生产结果。以下内容必须单独交代：

- 没有接入 YouTube 生产模型、线上流量和延迟用户满意度指标。
- 当前支持的候选动作有限，尚未完成让研究员阅读源码后生成任意新算法并验证的能力。
- 角色、日志和验证反馈是否真的优于简单单角色/固定规则，尚需消融实验。消融就是每次拿掉一个部件，看效果是否改变。
- 固定回复的离线演示只能检查流程，不能证明模型会提出有价值的解释。
- 跨模拟环境验证不能单独证明跨真实数据集泛化，也不能单独识别偏差的因果机制。
- 反馈回流后若没有改变下一轮决策，飞轮仍只是文件连接。应通过反证后改变实验的问题来检验它。

对我们而言，最重要的完成标准是：研究员发现收益中的偏差代价，提出可以被推翻的解释，用独立程序执行与评价，遇到反证后修正下一步。这比目录数量、角色数量或提示词长度更接近推荐系统研究。

## 9. 本次新增能力的代码落点

本节对应本项目的实现，不是作者目录。

| 位置 | 负责的事情 | 特意不承担的事情 |
|---|---|---|
| `rsi_researcher/research/journal.py` | `ExperimentJournal` 把开发轮次、候选身份和后续验证关联；`research_history()` 返回能直接交给研究员的历史。 | 不复制模拟环境的隐藏偏好真值，不把复用结果计成独立重复。 |
| `rsi_researcher/research/validation.py` | `run_validation()` 冻结开发候选，按预定协议生成新环境，重新执行原版和候选，保留各环境结果并写回日志。 | 不调用诊断、设计、复核、总结角色来临时改候选，不宣称线上发布或统计晋升。 |
| `rsi_researcher/research/operators.py` | 把一项确定的修改差分变成实际笔记或排名变化。 | 不自己决定这项修改是否有效。 |
| `rsi_researcher/research/evidence.py` | 把程序评分和笔记变化整理成可查证的逐条证据。 | 不把隐藏偏好表交给研究角色。 |
| `tests/test_journal.py`、`tests/test_validation.py` | 检查验证回流、路径搬移、新原版执行、候选冻结和失败保留等关键行为。 | 测试通过不等于实际模型研究能力已获证实。 |

验证汇总先在同一随机种子内合并不同条件，再保留逐种子结果；某个条件没跑完，会显式留下空值和失败记录，不通过只平均成功条件来隐藏问题。源事件重放尚缺可迁移的事件选择规则时，会返回 `needs_new_root_rule`，意思是“需要新的根事件选择规则”，不把同名事件当成同一个因果来源。

## 10. 继续借鉴差分与候选多样性时的具体边界

保存差分后，后续可以逐步扩大研究动作的范围。例如先让研究员选择已有的未知反馈规则，再允许提出新的反馈语义，最后在明确的函数接口内生成小范围代码修改。每扩大一级，都需要实际执行工具和独立评测支撑；目前不能用一段新提示词就宣称完成了新算法发现。

候选多样性可以按研究价值组织：沿着已有支持方向改善参数，测试一个竞争机制，尝试一种结构性变化。这里的“探索”是研究路线的探索；它与推荐系统对用户增加新曝光、收集真实反馈的 exploration 动作不同。当前固定日志不能回答用户看到新物品后会怎样反馈。

我们也不强行给每轮塞满三个类别。预算不足时，应说明本轮选择哪条路线以及为什么；日志记录未选择的竞争解释，后续再验证。多样性策略、日志摘要策略和独立验证反馈是否有帮助，都应该成为可关闭的研究部件，最终用消融比较，而不是仅靠流程图判断有效。
